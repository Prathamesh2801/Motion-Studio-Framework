# The Pack Engine — data-driven motion graphics

**Status: Phases 2 and 3 built and verified.**

The engine is live and has a real consumer. `npm run editor` opens an
application where choosing a player from a dropdown swaps the entire animated
presentation — portrait, name, number, crest, flag, league mark, five figures,
season, competition and accent colour — with no code change, no new composition
and no MP4 render. The Remotion template is imported as a React component and
fed JSON.

Shipped: `engine/`, `packs/`, `studio/`, the shared resolver, five new
primitives, four ViewModel-driven scene templates, three broadcast brands, the
`football-player-stats` pack with six player documents, and
`subject-showcase` (the domain-free reference pack a new pack is copied from).
See §10. Decisions taken during the build are recorded in place: packs mount
through `PackHost` (§3.3), the pure data layer imports real paths rather than
`@/` (§10), Studio gets no `schema` prop (§3.3), and packs declare their own
editor dropdowns via `facets` (§6).

This document designs a new subsystem inside Motion Studio Framework: a
**Dynamic Motion Graphics Engine** whose output is determined by data, not by
JSX. Its first product is a Football Player Statistics template; its purpose is
to also carry cricket, F1, esports, league standings, product showcases and
formats that do not exist yet, without any of them touching animation code.

layout primitives, a shared component system and a theme system. **Most of that
is already built in this repo and is working.** Rebuilding it would be the
single most expensive mistake available here, so the design below extends the
existing rings rather than starting a parallel tree.

**What genuinely does not exist yet, and is therefore the real scope:**

1. **A Vite React application.** The README states outright: *"There is no Vite."*
   Today the only host is Remotion Studio. This is the largest new piece.
2. **A live-editable data layer.** Today content is hard-coded in each project's
   `content.js`. There is no store, no editor, no JSON documents, no persistence.
3. **A concept of a reusable, data-parameterised video product.** Today
   `projects/registry.js` lists *films* — one entry, one video. Nothing in the
   repo expresses "one template, N datasets".
4. **Sports/domain semantics** — subject cards, progress bars, rating arcs,
   crest/flag/kit layouts.

Everything below is designed against that gap.

## 1. The idea: a Pack

A **project** is one video. A **pack** is a *video product*: a template plus a
data contract, from which unlimited videos are generated by swapping the data.

```
project  = component + fixed content        → one MP4
pack     = component + schema + adapter     → one MP4 per data document
```

A pack is the unit the editor browses, the unit Remotion registers, and the unit
that scales to cricket/F1/product. Adding "Cricket Batting Card" is adding a pack
folder — never an engine change. This mirrors the rule the framework already
follows everywhere else: *new capability arrives as a registry entry.*

### Pack manifest (the contract)

```js
// packs/football-player-stats/pack.js
export const pack = {
  id: 'football-player-stats',
  title: 'Football — Player Statistics',
  category: 'sports',
  Film: PlayerStatsFilm,          // the ONE component both hosts mount
  schema: playerStatsSchema,      // zod — validates a data document
  adapter: toViewModel,           // domain JSON  →  generic ViewModel
  timeline: buildPlayerTimeline,  // (data, fps) → timeline
  duration: (fps, data) => buildPlayerTimeline(data, fps).durationInFrames,
  formats: ['landscape', 'reel', 'square'],
  themes: ['broadcastDark', 'broadcastLight', 'terrace'],
  samples: [messi, ronaldo, haaland],   // shipped JSON documents
};
```

Nothing else in the system needs to know what football is.

- `studio/` — the only folder that knows about the DOM, forms, or the browser.

## 3. How the React app and Remotion share one component library

This is the crux of the brief, and it has exactly one correct answer.

### 3.1 The constraint

Framework components read time through `useCurrentFrame()` (via `useMotion`,
`useCountUp`, `useSceneProgress`). That hook requires Remotion's timing context.
Rendering `<StatCard>` in a plain React tree **throws** — there is no frame.

So "use the same components in a normal React app" cannot mean "render them
outside Remotion". It means: *put a Remotion timing context inside the React app.*

### 3.2 `@remotion/player` is that context

`<Player>` from `@remotion/player` mounts a composition inside any React DOM app,
with a real frame clock, seeking, and play/pause — no bundling, no rendering, no
server. It is already present in `node_modules` transitively; it must be promoted
to an explicit dependency in `package.json`.

```
                    ┌─────────────────────────────┐
                    │  packs/football-player-stats│
                    │       Film.jsx  (ONE)       │
                    └──────────────┬──────────────┘
                                   │
                  ┌────────────────┴────────────────┐
                  │                                 │
        ┌─────────▼─────────┐            ┌──────────▼──────────┐
        │  <Composition/>   │            │     <Player/>       │
        │  Root.jsx         │            │  studio/Stage.jsx   │
        │  Remotion Studio  │            │  Vite editor        │
        │  + CLI render→MP4 │            │  live, no rebuild   │
        └───────────────────┘            └─────────────────────┘
```

There is no second implementation, no `.web.jsx` variant, no re-export shim.
`Film.jsx` does not know which host mounted it.

### 3.3 One resolver so the two hosts cannot diverge

The failure mode to design out is *drift*: the Player showing 1920×1080 at 30fps
with theme A while the render produces 1080×1920 at 30fps with theme B. Both
hosts therefore derive their mount props from a single pure function.

```js
// packs/resolve.js
export const resolvePack = (pack, document, formatId) => {
  const data   = normalize(pack.schema.parse(document));
  const format = FORMATS[formatId ?? data.format];
  const theme  = resolveThemeRef(data.theme);          // brand + overrides
  return {
    component: withTheme(pack.Film, theme),            // shared Ring-1 helper
    inputProps: { vm: pack.adapter(data) },            // ViewModel, not raw JSON
    durationInFrames: Math.round(pack.duration(format.fps, data)),
    fps: format.fps,
    width: format.width,
    height: format.height,
  };
};
```

```jsx
// Remotion host — src/packs/register.jsx
// Props are the serialisable {packId, document, format}; `calculateMetadata`
// runs `resolvePack` to derive duration and dimensions from the CURRENT props,
// so editing the document changes the film's length.
<Composition id={`${pack.id}-landscape`} component={PackHost}
             defaultProps={{ packId: pack.id, document, format: 'landscape' }}
             calculateMetadata={packMetadata} />
```

> **No `schema` prop, deliberately.** Handing the document schema to
> `<Composition>` crashes Studio's props sidebar: its editor assumes every
> `string`-typed node holds a string (`ZodSwitch.js:39` calls
> `value.startsWith(...)` unguarded), and a document legitimately contains
> `z.union([z.string(), z.object({...})])` assets that are absent — an optional
> portrait arrives as `undefined` and the panel throws before drawing a field.
> Reshaping the data contract to suit a sidebar widget would be the wrong trade,
> so Studio falls back to editing props as JSON — the right surface for a
> document, and the same JSON the Vite editor edits. Validation is unaffected:
> `resolvePack` parses with `pack.schema` on every props change and throws with
> the offending field named.

```jsx
// React host — src/studio/preview/Stage.jsx
const mount = resolvePack(pack, liveDocument, format);   // recomputed on edit
<Player {...mount} controls loop
        style={{ width: '100%' }} acknowledgeRemotionLicense />
```

Same function, same numbers, same theme wrapper, both hosts.

`withTheme` currently lives private inside
[registerProject.jsx](src/framework/render/registerProject.jsx) with a component-identity
cache (so re-renders don't remount). The Player needs exactly that cache — a new
component identity on every keystroke would remount the composition and restart
the animation on every character typed. **The one Ring-1 change this design
requires is exporting that existing helper.** No new behaviour.

### 3.4 Why live updates need no rebuild

`inputProps` is a prop. Changing the document changes the prop; React re-renders;
`<Player>` re-renders the current frame with the new data. Counters, layouts and
bars all recompute because they are pure functions of `(frame, props)`. Code
changes are handled by Vite HMR. Neither path rebuilds anything.

One caveat worth stating now: `<Player>` re-parses `inputProps` on identity
change, so the editor must keep the document object stable between edits
(reducer returns the same reference when nothing changed) and debounce
text-field keystrokes (~120ms) before committing to the store. Otherwise typing
a player's name re-mounts the frame clock repeatedly and the preview stutters.

### 3.5 Two bundlers, one source tree

Remotion bundles with webpack via `remotion.config.js`; the editor bundles with
Vite. Both must agree on two things or imports break in one host only:

- the `@/ → src/` alias (webpack: already configured; Vite: `resolve.alias`)
- Tailwind v4 (webpack: `@remotion/tailwind-v4`; Vite: `@tailwindcss/vite`,
  pointed at the same [src/styles/tailwind.css](src/styles/tailwind.css))

`src/index.jsx` stays Remotion's entry. Vite gets its own `index.html` +
`src/studio/main.jsx`. They never import each other.

## 4. The data system

### 4.1 The rule that makes this scale

> **Scenes consume a ViewModel. Packs own the domain vocabulary.**

A scene that reads `data.player.goals` is a football scene forever. A scene that
reads `vm.metrics[i]` is a scene for football, cricket, F1, revenue and churn.

So the football JSON is written the way a human wants to write it — `player`,
`club`, `goals`, `assists` — and `packs/football-player-stats/adapter.js` maps it
into the generic ViewModel. **The adapter is the only file in the entire system
that contains the word "goals".** Every animation, layout and component sits
below it and sees nothing but generic shapes.

### 4.2 The ViewModel contract (`engine/viewmodel.js`)

```js
{
  subject: {                       // "who or what is this about"
    name, shortName, secondaryName,   // "Lionel Messi" / "Messi" / "La Pulga"
    badgeValue,                       // "10"  (jersey number, car number, rank)
    role,                             // "Right Winger" / "Batsman" / "Driver"
    portrait,                         // Asset
  },
  identity: [                      // small labelled chips — crest, flag, league
    { id, label, value, icon: Asset }
  ],
  metrics: [                       // THE core array. Order = display order.
    { id, label, value, display,      // display: pre-formatted string override
      format: 'plain'|'separated'|'compact'|'decimal',
      decimals, prefix, suffix,
      max,                            // present → renders as a progress bar
      emphasis: 'hero'|'normal'|'muted' }
  ],
  context: [                       // season, competition, "as of" date
    { id, label, value }
  ],
  assets: { background, logo, watermark },
  accent: '#RRGGBB' | null,        // data-driven brand accent (club colour)
}
```

Design notes:

- `metrics` is a flat array, never `{goals, assists, matches}`. This is what lets
  the same `StatBoard` render 5 football metrics, 3 F1 metrics or 8 product
  specs with zero component changes, and what lets the editor's data form be
  generated rather than written.
- `max` is what distinguishes a counter from a progress bar — a *data* decision,
  not a JSX one. Average Rating (7.9 / 10) gets a bar; Goals gets a counter.
- `emphasis: 'hero'` promotes one metric into `MetricSpotlight` — again data.
- `accent` lets Messi's card go Barça-blue and Haaland's City-blue *from the JSON*,
  through `extendTheme`, without a new brand file per club.

### 4.3 The document envelope (`engine/schema/document.js`)

Every pack's JSON shares this outer shape, so the editor, validator and
persistence layer work for packs that do not exist yet:

```json
{
  "$schema": 1,
  "pack": "football-player-stats",
  "id": "messi-2012",
  "format": "landscape",
  "theme": { "brand": "broadcastDark", "accent": "#A50044" },
  "timing": { "pace": "normal" },
  "data": { /* pack-specific — validated by pack.schema */ }
}
```

### 4.4 The football document (`packs/football-player-stats/data/messi.json`)

```json
{
  "$schema": 1,
  "pack": "football-player-stats",
  "id": "messi-2012",
  "format": "landscape",
  "theme": { "brand": "broadcastDark", "accent": "#A50044" },
  "data": {
    "player": {
      "name": "Lionel Messi",
      "shortName": "Messi",
      "number": 10,
      "position": "Right Winger",
      "nationality": { "name": "Argentina", "code": "ARG", "flag": "flags/arg.svg" },
      "portrait": "players/messi.png"
    },
    "club":   { "name": "FC Barcelona", "shortName": "Barça", "logo": "clubs/barcelona.svg" },
    "league": { "name": "LaLiga", "country": "Spain", "logo": "leagues/laliga.svg" },
    "season": "2011/12",
    "competition": "All competitions",
    "stats": {
      "goals": 73, "assists": 29, "matches": 60,
      "minutes": 5100, "rating": 9.1
    }
  }
}
```

Swapping this file for `ronaldo.json` produces a different video through the same
layout, the same animations and the same components. That is the Phase 3
acceptance test, stated as a test rather than a hope (§8).

### 4.5 Where hard-coding is still allowed

The brief says *no values hardcoded inside JSX*. The workable version of that
rule, and the one this design enforces:

- **Content** (names, numbers, labels, asset paths) — always data. Never in JSX.
- **Design tokens** (colour, type scale, spacing, radii) — never literals in JSX
  either; they come from `useTheme()`. Already enforced by the existing contract.
- **Motion tokens** (durations, stagger, curves) — imported from
  `framework/motion`, not typed as numbers. Already the house rule.
- **Structure** (this scene puts the portrait left and the stats right) — *is*
  the component. That is what makes it reusable. Layout variants are named
  variants (`layout: 'portrait-left' | 'portrait-right' | 'stacked'`) selected by
  data, not arbitrary geometry in the JSON.

## 5. Animation and layout primitives

### 5.1 Reuse, don't rebuild

Every animation named in the brief already exists except three. The pack uses the
existing library through the existing `preset` resolvers — no new animation code
for fade, slide, flip, scale, blur reveal, counters, image reveal, text reveal or
background movement.

### 5.2 The genuine gaps (new Ring-1 components, ~4 files)

| New | Why it doesn't exist yet | Built from |
| --- | --- | --- |
| `ProgressBar` | Nothing in the repo animates a bounded value to a track | `animate()` + theme tokens |
| `RatingArc` | Radial variant for 0–10 ratings | `@remotion/shapes` + `drawLine` |
| `CountUp` | `useCountUp` exists but only `StatCard` consumes it; the pack needs a bare animated number inside custom layouts | `useCountUp` + `Text` |
| `SplitText` | Per-character/word text reveal for the name lockup | `Stagger` + `Text` |

Each is a component over existing primitives, not a new engine. All four are
brand-agnostic and belong in `framework/components/`, not in the pack — a rating
arc is not a football concept.

### 5.3 New scene templates (Ring 2.5)

`SubjectIntro`, `StatBoard`, `MetricSpotlight`, `IdentityCard` — each takes a
slice of the ViewModel, arranges existing components through `Split`/`Stack`/
`Grid`, and reflows across the four format buckets for free. They are written
once and inherited by every future pack.

### 5.4 The invariant

> An animation never receives a player. It receives a value, a delay and a duration.

Enforceable by inspection: no file under `framework/` or `templates/` may contain
a domain noun. Worth a lint rule in `scripts/verify.mjs` (§8).

## 6. The editor application

```
┌──────────────────────────────────────────────────────────────────┐
│  Pack ▾   Subject ▾   Theme ▾   Format ▾            [Export MP4] │
├──────────────┬───────────────────────────────────┬───────────────┤
│  SUBJECTS    │                                   │   DATA        │
│  ◦ Messi     │        <Player />                 │  Name  [    ] │
│  ◦ Ronaldo   │      (live, seekable)             │  No.   [ 10 ] │
│  ◦ Haaland   │                                   │  Goals [ 73 ] │
│  + New       │                                   │  ...          │
│              │  ├────────●──────────┤  0:04/0:12 │   ASSETS      │
│  LEAGUES     │  ◦ landscape ◦ reel ◦ square      │  [portrait]   │
│  ◦ LaLiga    │                                   │  [crest]      │
└──────────────┴───────────────────────────────────┴───────────────┘
```

- **State**: React context + `useReducer`, persisted to `localStorage`. No new
  dependency — the state is one document object and a few selections; a store
  library would be ceremony. Every panel dispatches; `Stage` is the only reader
  that matters.
- **Dropdowns are declared by the pack, not written by the editor.** A pack
  ships `facets` — a list of `{ label, options: [{ label, patch }] }` — and the
  application renders a `<select>` for each. This is how League / Season /
  Competition exist without the editor containing the word "league"; a cricket
  pack declaring `Format → Test | ODI | T20` gets working dropdowns with no
  editor code. Enforced: `npm test` greps `studio/` for domain nouns, and it
  caught a real leak ("Using club colour" on a button) during the build.

  An option carries a **patch**, not a value, because these choices are
  compound: picking a league changes its name *and* its logo, and a control that
  changed only the name would leave the previous badge on screen.

  Selection is read back off the document with `patchMatches` rather than stored
  beside it — one source of truth, so a dropdown cannot disagree with what is on
  screen, and a raw JSON edit updates the dropdowns automatically.
- **Assets**: dropped files become `URL.createObjectURL` blobs for instant
  preview; the JSON stores a `public/` path for render parity. The editor warns
  when a blob-only asset would not survive an MP4 render — a real trap, since the
  preview would look correct and the render would not.
- **Validation is live and non-blocking**: an invalid document shows the error on
  the field and keeps rendering the last valid frame, rather than throwing away
  the preview.
- **Export**: renders are a CLI/server concern. The editor writes the document to
  `packs/<id>/data/<name>.json` (dev-server endpoint) and shows the exact
  `npx remotion render` command. A local render API is optional and later.

## 7. How this scales to the next twelve templates

| New thing | What it costs |
| --- | --- |
| Ronaldo instead of Messi | a JSON file |
| A new club's colours | one field (`theme.accent`) |
| Reel version of an existing pack | one entry in `pack.formats` |
| Cricket batting card | a pack folder: schema + adapter + timeline + Film |
| F1 driver card | a pack folder (reuses `StatBoard`, `IdentityCard` unchanged) |
| League standings / bracket | one new scene template + a pack |
| Product showcase | a pack; `metrics` become specs, `subject` becomes the product |
| A new visual style | a brand in `design/brands/` |
| A new animation | one entry in the existing preset registry |

None of those touch `framework/` after §5.2 lands. That is the test of whether
this architecture is real.

## 8. Verification (how we prove the claim rather than assert it)

The framework already has `npm test` (pure Node) and `npm run verify` (stills +
compositions). Three additions make the "data-only" claim falsifiable:

1. **Adapter tests** — `messi.json` and `ronaldo.json` through
   `pack.adapter` produce valid ViewModels; a malformed document produces a named
   error, not `undefined`.
2. **The swap test** — render frame 90 of the same pack with three documents and
   assert the three stills differ, while the *component tree* (a rendered
   structure snapshot) is identical. This is the literal Phase-3 acceptance
   criterion from the brief, as an automated check.
3. **A domain-noun lint** — grep `framework/` and `templates/` for the pack's
   vocabulary and fail the build on a hit. Cheap, and it is what stops the
   architecture eroding six packs from now.

## 9. Decisions taken (with reasons), so they can be argued with

| Decision | Alternative rejected | Why |
| --- | --- | --- |
| `@remotion/player` in a Vite app | Re-implement components with a mock frame context | A second implementation is the exact duplication the brief forbids |
| Vite app added **alongside** Remotion Studio | Vite replaces Studio | Studio remains the best tool for timeline/props debugging and is what `verify` drives; they cost nothing to keep both |
| `metrics[]` flat array in the ViewModel | Named stat fields | Named fields make every scene sport-specific and kill the generated editor |
| Pack owns the adapter | Generic JSON authored by hand | Human-readable JSON is the product; the adapter is 30 lines and buys the entire abstraction |
| Context + `useReducer` | Redux / Zustand | One document object; a store library adds a dependency and no capability |
| New rings `engine/` + `packs/` + `studio/` | Put it all in `projects/` | A project is one video; conflating "one video" with "a template product" is what makes engines rot |
| Export `withTheme` from Ring 1 | Duplicate the wrapper in `studio/` | Duplicating it duplicates the identity cache, and a cache miss restarts the animation on every keystroke |

> **Note added during the build.** The pure data files (`engine/*`, and a pack's
> `schema.js` / `adapter.js` / `timeline.js`) import real relative paths, not
> `@/`. Two reasons, both about keeping `npm test` bundler-free: `@/` is a
> bundler alias Node cannot resolve, and `framework/index.js` re-exports `.jsx`
> Node cannot parse. Files containing JSX keep using `@/framework` — nothing
> outside a bundler was ever going to load them. This is why the whole data
> pipeline is asserted in plain Node today.

**The swap test** (`scripts/test.mjs`) is the acceptance criterion as code. It
asserts that two documents produce an *identical* beat plan, in the same order,
with the same lengths, and the same metric slots — while every visible value
differs. Two stills looking different is not proof the template was reused;
identical structure with different content is.

### Assets

`public/packs/football-player-stats/` holds **generated placeholders** — abstract
silhouettes, geometric shields, flags built from real band layouts. Real
photographs and crests belong to somebody else, and committing them would make
this repo undistributable. They are unmistakably not the real thing on purpose.

Replace any file at the same path and nothing in the code changes. Regenerate
with `node scripts/make-football-placeholders.mjs`.

## 11. Adding the next pack

Football is the blueprint. To add cricket, F1, esports or a product showcase:

1. Copy `src/packs/football-player-stats/`.
2. Rewrite four files — `schema.js` (the JSON in its own vocabulary),
   `adapter.js` (→ ViewModel), `timeline.js` (the beats), `Film.jsx` (the scene
   map). None of them contains an animation.
3. Declare `facets` for whatever dropdowns that domain needs.
4. Ship documents in `data/` and assets in `public/packs/<id>/`.
5. Add one line to `packs/registry.js`.

`engine/`, `packs/resolve.js`, `PackHost`, the hosts, the editor, the brands and
the four scene templates are untouched. That is the test of whether this
architecture is real — and it is why the reference pack still exists: it is the
worked example, kept domain-free so it cannot quietly acquire football
assumptions.
